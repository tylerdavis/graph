`plan_and_execute` is the third way a plan runs: the LLM **planner** authors a plan on the fly for a novel multi-step task, and the same pipeline executes it — same template language, same control steps, same finish modes. It exists so that improvised work still gets plan-shaped execution: typed dataflow between steps instead of the agent eyeballing intermediate results, and a visible artifact you can inspect afterwards.

```text
→ plan_and_execute {"query":"which of last sprint's bugs are still open?"}
  ✎ planning…
  → linear__list_cycles …
  → linear__list_issues …
  ✎ synthesizing answer…
```

It appears in the catalog as a bare reserved tool (alongside the namespaced `plan__*` tools), so it's callable from chat, from a plan step, or directly. In chat, the [router](/using/tool-selection) reaches for it when a task is multi-step and no authored plan matches.

## What the planner sees

The `planner`-role model drafts against:

- **The full tool catalog** — every tool's description and input schema. Descriptions and exemplars are routing signals here too: they steer which tools the planner picks.
- **Output shapes** — a declared output schema when one exists (MCP-provided, a `tool_overrides` entry, or a user tool's `output_schema`), otherwise the [shape cache](/tools/shape-cache)'s observed shape, marked as empirical. The cache is read fresh at every planning attempt, so a shape observed earlier in the same run is already available to the next plan.
- **Your context** — the `[user]` config section, same as the chat agent.

With no shape at all for a tool, the planner is instructed to use whole-result references (`{{E0}}`) or to stop and continue planning after real results exist — cold caches degrade, they don't break.

## What the planner is instructed to do

The planner has the full step vocabulary — [exit gates](/plans/exit-gates), [route](/plans/branching), [map/reduce](/plans/iteration), and `plan__*` composition — plus standing instructions that shape its drafts:

- **Exit gracefully rather than fabricate.** When data comes up empty, draft an `exit` with an honest message instead of inventing results.
- **Gate check-shaped plans.** Validations and assertions end in explicit gated exits, not solver prose.
- **Infer per item, not per list.** Inference over a list becomes a `map` body calling [`builtin__infer`](/tools/builtins#builtin-infer) with `{{item}}`, and when [roles with descriptions](/models/models-and-providers#custom-roles) are configured, those descriptions steer each call to the smallest adequate model.

## Replanning

Planner-authored plans are drafts, so defects trigger a **replan** instead of a hard failure: the error — including, for bad data references, a digest of the keys that actually exist — feeds back to the planner, which revises the plan. Executed steps are preserved and never re-run; only the broken tail is replaced. After the configured attempts (`[settings].planning_attempts`, default 2), it degrades to an honest error summary.

`EmptyData` never triggers a replan — a search that found nothing is an answer, not a defect, and replanning can't conjure data. The full policy, including why _your_ plans never replan, is in [Errors & replanning](/plans/errors-and-replanning).

## Cost

A chat turn through `plan_and_execute` is 4+ inference calls: the agent (deciding to plan), the planner, the solver, and the agent again (reading the report) — plus one planner call per replan. The plan's steps themselves are still zero-inference. When the workflow is worth keeping, freeze it: an authored plan runs the same steps for 1 call (solver) or 0 ([output/silent](/plans/finish-modes)), and [never replans](/plans/errors-and-replanning). See the full [cost table](/reference/scripting-contract#inference-cost-by-invocation).

## Drafting without executing

**Draft-only** planning produces a plan for you to review instead of executing it. A draft is the built-in plan [`compose_plan`](#composing-a-whole-plan-in-one-call), so `graph plan draft`, MCP `graph_plan_draft`, and the [workbench](/workbench/plan-workbench) run the same plan, which can be inspected with `graph plan show compose_plan` and replaced by a plan file with the same identifier.

### Composing a whole plan in one call

The built-in plan `compose_plan` drafts a whole plan in one call. `graph plan draft`, MCP `graph_plan_draft` and the workbench run it; `graph plan run compose_plan --input goal="…"` runs it directly. It returns `{plan, valid, problems, yaml, needs, questions}`, or `{plan: null, missing}` when no tool can do part of the goal.

1. **Needs.** One `builtin__infer` call on the `outliner` role (`needs_model` picks another) lists the plan's inputs, its capabilities in order (each `data`, `judgment` or `control`), and the details the goal states, such as an identifier format or a path.
2. **Tools.** [`search_tools`](/tools/finding-tools) runs once per `data` capability, in parallel.
3. **Missing capabilities.** When search finds nothing for a `data` capability, the plan stops with `missing` before any drafting, so a gap is reported instead of being filled with an `agent` or `builtin__infer` step.
4. **Draft.** One `builtin__infer` call on the `planner` role (`model` picks another) writes the whole plan as YAML. Its system prompt holds the composing rules, a worked example, the template rules and the tools every plan can use, so it caches; the request holds the goal, its needs and the tools search found, described with their schemas by `builtin__compose_context`. Along with the YAML, it lists in `questions` each value it had to guess because neither the goal, the inputs nor the tools' schemas pin it down, such as a status or project name, and uses its guess in the plan. When part of the plan needs a tool it wasn't shown, it says what that tool should do in `search`; it decides when, and leaves `search` empty otherwise.
5. **Clarify.** Only when there are questions: `builtin__question_form` turns them into one [`ask`](/plans/ask-step) form, one field per question (a pick list when a tool's schema lists the allowed values) plus an open "Anything else the planner should know?" field, with the guesses prefilled. When nobody can answer (CI, a client without elicitation), the plan keeps its guesses.
6. **Check and fix.** `builtin__check_plan` parses the YAML and validates it: structure, templates, the catalog, a tool's required inputs, plan inputs passed to a parameter of another type, `exit`/`route`/`filter` conditions with an unknown operator, steps whose result nothing uses, references to a field a tool's declared or observed output doesn't have, and the composing rules (an `agent` step lists its tools; `agent__chat` is never used). The plan is settled when it is valid, nothing is left to search for, and any answers are in. Until then, up to three rounds each make one call that returns a YAML patch of only the steps that need to change (a list, or a mapping keyed by step id), and `builtin__check_plan` applies it and validates again. Every round sees the answers to the questions as requirements: an answered value replaces the guess, a value the answer says changes from run to run becomes a plan input or an `ask` step, the open field is followed as an instruction, and a problem is never fixed by dropping something the answers asked for. A round can also ask for tools in `search`; `builtin__find_tools` runs `search_tools` for each request and the next round sees what it found. The whole plan is never redrafted.

The plan it writes takes the values the user supplies as `input_schema` inputs and finishes with an `output` map.
