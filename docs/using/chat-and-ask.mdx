`ask` and `chat` run graph's agent loop — the conversational surface for probing tools, prototyping workflows, and exercising plans. Every tool call here also feeds the [shape cache](/tools/shape-cache), so exploration makes the planner smarter. Anything you'll run twice belongs in a [plan](/plans/overview), and plans get their own surface: the [workbench](/workbench/plan-workbench).

## One-shot: `graph ask`

```bash
graph ask "Summarize open urgent issues"
graph ask "Now group them by project" --thread            # continue latest thread
graph ask "…" --thread 62dac762e251                       # continue a specific thread
```

- **Streaming**: the answer streams to stdout; tool activity (dim `→ tool {args}` / `✓ tool 0.8s` lines) goes to stderr. `graph ask "…" > out.md` captures just the answer.
- **Piped stdin** becomes context:
  ```bash
  git diff | graph ask "review this change"
  cat error.log | graph ask "what's failing?"
  ```
- **`--json`** buffers and emits a machine-readable envelope instead:
  ```json
  {
    "content": "…the answer…",
    "tool_calls_made": 3,
    "usage": {
      "calls": 4,
      "input_tokens": 2055,
      "output_tokens": 100,
      "cost_usd": 0.0077,
      "by_step": [{ "path": "chat", "calls": 4, "cost_usd": 0.0077 }],
      "by_model": [{ "provider": "anthropic", "model": "claude-sonnet-5", "calls": 4 }]
    },
    "thread_id": "62dac762e251"
  }
  ```
  `usage` covers the whole turn, including tokens spent inside any `plan__*`
  tool the agent called — its solver and its steps, not just the agent's own
  rounds. `cost_usd` appears only when [`[pricing]`](/reference/configuration#pricing--per-model-token-prices)
  is configured; the full shape is in [what a run spent](/reference/scripting-contract#what-a-run-spent).
- **`--no-stream`** prints the final answer only, without token streaming.

<Warning>
Put `--thread` **after** the message. It takes an optional value, so `graph ask --thread "question"` parses the question as a thread id.
</Warning>

## Interactive: `graph chat`

```bash
graph chat                      # new thread with the default chat agent
graph chat search_bot           # new thread with a named agent
graph chat --thread             # resume the most recent
graph chat --thread <id>        # resume a specific one
```

Slash commands inside the REPL:

| Command | Effect |
|---|---|
| `/agent` | list the agents, marking the one you're talking to |
| `/agent <name>` | switch to another agent for the rest of the conversation |
| `/thread` | show the current thread id, title, and owner |
| `/state` | dump the active agent's view of the conversation (including tool calls) as JSON |
| `/quit`, `/exit`, `/q` | leave (Ctrl-D also works) |

Each completed turn prints a dim one-line usage summary to stderr — calls,
tokens, and cost when [`[pricing]`](/reference/configuration#pricing--per-model-token-prices)
is set. It is per turn, not cumulative for the session.

A failed turn keeps the session alive and rolls the conversation back so a retry starts clean. On exit you get a copy-pasteable resume hint:

```
resume with `graph chat --thread 8d36b7003df9`
```

## Agents

`chat` and `ask` run the built-in [`chat` agent](/reference/agent-schema) unless you name another one (`graph chat <agent>`, `graph ask --agent <agent>`). An agent can work with others in two ways, declared in its file:

- **Subagents** (`subagents`): the agent calls `agent__<name>` and another agent runs the request in its own fresh context, then returns its answer. The run is kept in the thread but never shown to the caller, which sees only the answer.
- **Handoffs** (`handoffs`): the agent calls `transfer_to_<name>` and the other agent takes over the conversation, picking up the current turn with a note on what is needed. With `wait_for_user: true` the turn ends at the handoff instead: the handing-off agent's reply is what the user sees, and the other agent answers from the user's next message. The thread remembers who is active, so a resumed thread continues with the agent that last had the conversation.
- **Handing back** (`transfer_back`): an agent that was handed the conversation can hand it back to the agent that handed it over, with a message saying what it did. It doesn't list that agent anywhere: every agent gets `transfer_back` whenever another agent handed it the conversation, and not when you started it directly. This is how a [drafter](#drafting-tools-and-agents) returns to whoever sent you to it.

Each agent sees your messages, what the other agents said, the handoffs, and its own tool calls, but not other agents' tool traffic. A turn hands off at most 4 times, handing back included; after that, whoever holds the conversation answers.

### Drafting tools and agents

Two built-in agents write new files with you, over as many turns as it takes:

- `graph chat tool_drafter` writes a [user tool](/tools/user-defined). It checks the catalog for an existing tool first, then writes the file, and test-runs it once on a sample input with `builtin__try_tool`, which asks you before anything runs and shows the command. A tool is saved only after a successful test run, or untested when you say you don't want it tested.
- `graph chat agent_drafter` writes an [agent](/reference/agent-schema), for conversation, for plan steps, or both. It picks the agent's tools from the catalog and saves the file once it validates against the catalog and your configured models; there's no test run, so try it yourself with `graph chat <name>` or an `agent__<name>` step.

Both save to the project (`./.graph/tools/` and `./.graph/agents/`), ask "Save it?" before writing anything, and never replace an existing file unless you agree. `graph ask`, which has no terminal to ask in, saves without asking. A saved tool or agent is usable right away in the same session. In the [workbench](/workbench/plan-workbench#drafting-a-tool-or-an-agent) the drafters work on a draft in the pane instead, which you save yourself.

A thread belongs to the agent it was started with. `graph chat <agent> --thread <id>` is refused when `<agent>` isn't that owner. Leave the agent out to resume, or switch with `/agent <name>` inside the REPL.

## Reading the output

```
→ plan__project_status {"project":"New Relic"}     ← agent called a plan tool
  → linear__list_projects {"limit":5,…}            ← steps indent under it
  ✓ linear__list_projects 631ms
  ✎ synthesizing answer…                           ← the plan's solver is writing
  …dim streamed report…                            ← solver progress (stderr)
✓ plan__project_status 8.8s
The migration is on track…                         ← the agent's answer (stdout)
```

Dim text is progress; solid text is the answer. The distinction matters for piping — only the answer is on stdout.
